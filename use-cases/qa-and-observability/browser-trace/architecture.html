How the recording works today shipping

The action list comes from the DOM, not from a trace

To be precise about what's running: the action list is built by an injected listener in the page — deterministic DOM-event capture. It is not CDP tracing, and not the Chrome DevTools Recorder. CDP is only the connection to the browser.

1

Inject once per session

On connect, a small script is added to every page and frame via addInitScript.

2

Listen for real interactions

Capture-phase listeners for click, change, keydown and scroll — the user's actual actions in the live view.

3

Describe each action

Per event: a priority list of selectors (id → aria → text → css → xpath), the element's live state (role, name, value, ARIA flags, visibility, box), and a timestamp.

4

Read it back

Events buffer in the page and are collected by the server, then merged with the Whisper transcript and the mapped source code.

Where CDP comes in: the same session is a real Chrome we fully control, so richer, CDP-native signals — the accessibility tree, console errors, network failures, DOM snapshots, and full session recording — are a natural next layer when a bug needs more than the DOM. available next

Where Browserbase fits

The browser is the hard part to own

A local Chrome with CDP can read the same signals — accessibility tree, console, network. The difference is everything around the browser. To do this yourself, you'd have to build and operate the browser layer. Browserbase is that layer, managed.

What it takesBuild & operate it yourselfOn Browserbase
Interactive, embeddable live viewBuild a screencast + input relay and keep it stable — a large effort on its ownHosted live view, embeddable in an iframe
Session recording & replayBuild and store it yourselfBuilt in
Reliability & isolationA browser running next to your app and model competes for resources and can destabilize the previewDedicated, isolated cloud Chrome
Running the browser at allA full browser alongside your app is heavy on RAM and costOffloaded to Browserbase
Scale & concurrencyManage your own poolThousands of concurrent sessions, warm pool
CDP traces (a11y / console / network)Possible locally, but you wire and maintain itSame CDP access, on managed browsers
A reliable, embeddable live view and a stable, isolated browser are significant engineering efforts in their own right. That's the gap Browserbase fills.
The next layer · a second CDP connection

Attach a read-only tracer without touching the session

Every Chrome target accepts multiple concurrent CDP clients. While the user drives the live session, we attach a second, listen-only client that records the full DevTools firehose and never sends an action — so tracing can't interfere with the repro.

The CDP firehose

Everything a screenshot can't tell you

The read-only client records the full protocol stream, joined by timestamp and sliced into per-page, searchable buckets — the exact evidence a fixer needs to move from "looks broken" to "here's the failing request and the line that swallowed it."

  • NetworkEvery request/response, status, timing, payloads — the failed or slow calls behind the bug.
  • Console & uncaught exceptionsThe errors thrown during the exact repro, in order.
  • Runtime & LogWarnings and runtime messages the UI never surfaces.
  • DOM snapshots + screenshots over timeState captured at intervals, joined to the CDP events by timestamp.
  • Page lifecycle & navigationsLoads, redirects and route changes across the flow.
  • Per-page buckets → agent loopStructured summaries feed the next iteration, so it learns from the last run.

Hard to get on a browser you run yourself

  • You must keep a real browser alive for the whole session.
  • Attach a second concurrent CDP client reliably, without it interfering with the driver.
  • Stream and store a high-volume firehose, then bisect it per page.
  • Keep it isolated so it doesn't destabilize the app or the model running beside it.

Browserbase sessions are built for exactly this: long-lived, isolated, multi-client.

Injected DOM listeners record each action with selectors + full element state. Deterministic; no model involved.

Voice now

Mic → OpenAI Whisper → transcript, interleaved with actions by segment timestamp. Swappable for Groq or Whisper Flow.

Deterministic: the recorded element's anchors → route file → the handler that renders it.
