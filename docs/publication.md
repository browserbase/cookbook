# Publication boundary

This checkout is private. It contains the `use-cases/` source collection, private catalog records, private provenance, and Git history that predates cookbook anonymization work. Passing repository tests does not make it safe to publish.

The normal boundary check verifies that every private recipe stays inside `use-cases/` and that catalog and source-manifest classifications agree:

```sh
python3 scripts/publication_boundary.py
```

A release process must create a new empty directory from the public catalog and provenance allowlist, then run the stricter check against that exact history-free artifact:

```sh
artifact_dir=$(mktemp -d)
python3 scripts/publication_boundary.py --export "$artifact_dir" --require-public
python3 scripts/publication_boundary.py --root "$artifact_dir" --require-public
```

The exporter copies each public recipe's complete working directory, the public
provenance and authorship records, generated recipe guides and task indexes, the
polished README and brand assets, the routing skill and plugin manifests,
contribution and community files, repository scripts and tests, and CI. It
refuses symlinked sources and non-empty destinations and never copies Git
history or the private collection.

`PUBLIC_EXPORT_REPORT.json` separates missing public provenance paths into a
reviewed allowlist with reasons and an unexpected list. The 22 reviewed paths
are upstream repository administration, release automation, generated bytecode
or downloads, an obsolete extension archive, and files removed by the ESLint
migration. Any new missing path fails export.

The strict check rejects private catalog or provenance records, a `use-cases/`
tree, Git history, symlinks, exact private recipe identifiers and paths, the
private upstream repository URL, secret-shaped values, broken local Markdown
links and images, and missing catalog paths, working directories, entrypoints,
manifests, upstream READMEs, or environment templates. A successful check proves
those structural and content exclusions only. It does not grant a license or
replace review of the final artifact and its metadata.

Do not publish this working tree or its Git history. Prepare a separate artifact, review the complete file list and rendered documentation, verify licenses, and run the strict check there.

## Release checks

The GitHub verification workflow builds the history-free artifact and runs its
strict boundary check, structural verifier, test suite, local Markdown link
check, and Gitleaks scan. It also clean-installs representative Python,
TypeScript, Go, Playbook, and integration recipes. These checks establish the
artifact's structure and local build health; they do not replace live tests
requiring credentials and external accounts.

Before enabling a public repository, review every file in the generated
artifact. Push only a new Git history created inside the reviewed artifact
directory.
